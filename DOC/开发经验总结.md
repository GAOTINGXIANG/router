# 开发经验总结(LAN8720 以太网 + DHCP server + WiFi STA + NAT 网关)

> 项目:ESP32-WROOM-32 + LAN8720,实现「以太网 DHCP server + WiFi STA 上行 + 软件 NAT 网关」
> 环境:ESP-IDF v6.0.2
> 最终成果:有线设备经 ESP32 NAT 上网,实测 **17 Mbps**(符合 ESP32 软件 NAT 10~20 Mbps 预期)
> 用途:沉淀本次踩坑与最佳实践,供后续同类开发参考

---

## 一、项目全景与最终架构

```
有线设备 ──以太网──► [LAN8720] ──► IP_FORWARD ──► NAPT ──► [WiFi STA] ──► 热点 ──► 互联网
                     (LAN, 192.168.4.1, DHCP server)          (WAN, DHCP client)
```

模块划分(严格解耦):

| 文件 | 职责 |
| --- | --- |
| `CODE/src/ethernet.c` | LAN:DHCP server + NAPT 启用 + DNS 下发 |
| `CODE/src/wifi.c` | WAN:STA 连接 + 默认路由 |
| `main/main.c` | 仅编排 `wifi_sta_init()` → `ethernet_init()` |

## 二、关键技术坑(按出现顺序,每个「现象 → 根因 → 正确做法」)

### 坑 1:C 预处理器宏参数个数陷阱

**现象**:`IP4_ADDR(&ip, ETH_STATIC_IP)` 报 `macro requires 5 arguments, but only 2 given`。

**根因**:预处理器**先按实参个数匹配、后展开宏**。`ETH_STATIC_IP` 是 `192, 168, 4, 1`,作为单个实参传进去后展开出的逗号已经太迟,导致内层宏参数错乱。

**正确做法**:不要用会展开成多个逗号分隔值的宏去填充另一个函数式宏的单个参数。用 ESP-IDF 官方宏做结构体初始化:

```c
.ip = ESP_IP4ADDR_INIT(192, 168, 4, 1)   // 或 .addr = ESP_IP4TOADDR(192,168,4,1)
```

### 坑 2:PHY 地址硬编码

**现象**:`eth_phy_802_3: power up timeout` → `lan87xx_init failed`。

**根因**:硬编码 `phy_addr = 0`,但模块实际地址是 **1**(PHYAD0 上拉)。MDIO 读回 0xFFFF(无设备应答),power-down 位恒为 1,等满 100ms 超时。

**正确做法**:

```c
phy_cfg.phy_addr = ESP_ETH_PHY_ADDR_AUTO;   // -1,驱动扫描 0~31 自动探测
```

### 坑 3:DHCP server 必须声明 `ESP_NETIF_DHCP_SERVER` 标志

**现象**:`esp_netif_dhcps_start` 返回 `ESP_ERR_ESP_NETIF_DHCPS_START_FAILED`,日志 `DHCP server cannot be started`。

**根因**:默认 `ESP_NETIF_DEFAULT_ETH()` 是 **DHCP 客户端**网卡。SDK 创建 netif 时**只有带 `ESP_NETIF_DHCP_SERVER` 标志才分配 `dhcps` 对象**(`esp_netif_new` 里 `if (flags & DHCP_SERVER) esp_netif->dhcps = dhcps_new()`)。默认网卡的 `dhcps == NULL`,`dhcps_start(NULL)` 返回 `ERR_ARG`。

**正确做法**:创建 netif 时把默认 flags 里的 `DHCP_CLIENT` 换成 `DHCP_SERVER`。

### 坑 4(最关键):NAPT 标志开在「LAN 网卡」,不是 WAN

**现象**:客户端 `ping 8.8.8.8` 全超时,但 WiFi 已拿到 IP、NAPT 也"启用成功"。

**根因**:lwIP 的 `netif->napt` 语义**反直觉**——标记的是**内网侧(待改写的源)网卡**,即**以太网(LAN)**,而不是 WAN(WiFi)。源码铁证(`ip4_napt.c:869`):

```c
ip_napt_forward(..., struct netif *inp, struct netif *outp) {
    if (!inp->napt) return ERR_OK;   // 入包网卡(以太网)带 napt 才做 SNAT
    ... 源改成 outp->ip_addr(出口网卡 = WiFi)IP ...
}
```

我把 NAPT 开在了 WiFi 上 → 入包网卡(以太网)`napt=0` → `ip_napt_forward` 直接返回,SNAT 根本没发生 → 源地址 192.168.4.x 原样出去,上游无法回程。

**正确做法**:`esp_netif_napt_enable(以太网网卡)`,源地址会自动改成出口网卡(WiFi)IP,无需写死。

> 这条是参考成熟项目 `esp32_ethernet_router`(martin-ger)后才醒悟的——它用 `ip_napt_enable(my_ap_ip, 1)` 开在以太网地址上。

### 坑 5:三条编译配置缺一不可

```ini
CONFIG_LWIP_L2_TO_L3_COPY=y   # WiFi 回程(DNAT 改 IP 头)需要 L2→L3 缓冲拷贝
CONFIG_LWIP_IP_FORWARD=y      # IP 跨网卡转发
CONFIG_LWIP_IPV4_NAPT=y       # NAT
```

- `IPV4_NAPT` 依赖 `IP_FORWARD`。
- `L2_TO_L3_COPY` 最容易被漏掉(它管的是 WiFi 驱动缓冲,不是直接叫"NAT"字眼),但回程 DNAT 需要。

### 坑 6:默认路由必须指向 WAN

WiFi(WAN)与以太网(LAN)都 up 时,转发的包必须从 WiFi 出去。虽然 route_prio(WiFi=100 > 以太网=50)理论上会选 WiFi,但**显式锁定最稳妥**:

```c
esp_netif_set_default_netif(s_sta_netif);   // 在 IP_EVENT_STA_GOT_IP 里调用
```

该调用会置 override 标志,之后以太网上线也无法抢占默认路由。

### 坑 7:DNS 下发是两步,且默认不下发

lwIP DHCP server 默认 **不** 下发 DNS,而且要两个独立动作:

```c
esp_netif_set_dns_info(eth_netif, ESP_NETIF_DNS_MAIN, &dns);   // ① 设 DNS IP(内部写 dns_server[])
uint8_t on = 1;
esp_netif_dhcps_option(eth_netif, ESP_NETIF_OP_SET,
                       ESP_NETIF_DOMAIN_NAME_SERVER, &on, sizeof(on)); // ② 打开 OFFER_DNS 位
```

两个都做了,DHCP offer 里才会带 option 6。

## 三、方法论经验(比具体坑更可迁移)

### 1. 报错先读 SDK 源码,不靠猜

本次几乎每个 bug 都是通过读 ESP-IDF 源码找到确切失败条件的:

| 报错 | 定位到的源码 |
| --- | --- |
| power up timeout | `esp_eth_phy_802_3.c` pwrctl(读回 power_down 位恒 1) |
| DHCP server cannot be started | `esp_netif_lwip.c` dhcps_start_api + `dhcpserver.c` dhcps_start |
| NAPT 不生效 | `ip4_napt.c` ip_napt_forward + `ip4.c` 挂钩点 |

**教训**:报错信息里的英文/错误码是线索,顺着它在 SDK 里 grep 对应函数,通常几分钟就能锁定根因,比反复试错快得多。

### 2. 参考成熟开源项目

`esp32_ethernet_router`(martin-ger/esp32_nat_router)是本项目最重要的外部参考——它的实现原理文档直接点破了 NAPT 方向的坑。**同类功能先找现成项目,尤其看它的 sdkconfig 和关键 API 调用位置**,比自己啃 API 文档快。

### 3. 模块解耦,NAT 连接在内核层

WiFi 与以太网各自独立文件、独立事件回调、互不 include;NAT 的"连接"由 lwIP 内核(默认路由 + `netif->napt` + 转发)完成。这样每块能单独调试,后续增减功能(如加 VPN、加 Web 管理)不动现有模块。

### 4. 事件回调里做容错,别滥用 abort

`ALREADY_STARTED` / `ALREADY_STOPPED` 这类"幂等"返回应视为正常,否则链路抖动会触发 abort。本次 NAPT/DHCP 的启停都改成 `ESP_LOGE/ESP_LOGW` 而非 `ESP_ERROR_CHECK`。

### 5. 时序敏感的操作放在「网卡 up」事件里

`esp_netif_napt_enable` / `esp_netif_dhcps_start` 都要求网卡已 up,所以要放在 `ETHERNET_EVENT_CONNECTED` / `IP_EVENT_STA_GOT_IP` 里,不能放在 init 阶段。

## 四、速查表(可直接复用)

### 关键 API 与调用位置

| 目的 | API | 调用位置 |
| --- | --- | --- |
| 以太网做 DHCP server | 建 netif 时 flags 加 `ESP_NETIF_DHCP_SERVER` | `ethernet_init()` |
| 启用 NAPT | `esp_netif_napt_enable(eth_netif)` | `ETHERNET_EVENT_CONNECTED` |
| 默认路由走 WAN | `esp_netif_set_default_netif(sta_netif)` | `IP_EVENT_STA_GOT_IP` |
| 设静态 IP | `esp_netif_set_ip_info()` | init(先 `dhcps_stop`) |
| 下发 DNS | `set_dns_info` + `dhcps_option(DOMAIN_NAME_SERVER)` | init(先 `dhcps_stop`) |

### 关键配置(sdkconfig.defaults)

```ini
CONFIG_LWIP_L2_TO_L3_COPY=y
CONFIG_LWIP_IP_FORWARD=y
CONFIG_LWIP_IPV4_NAPT=y
```

### 硬件/驱动要点

- LAN8720 RMII 时钟:IDF 6 是代码级配置,默认 `EMAC_CLK_EXT_IN` + GPIO0,与"25MHz 晶振 + nINT/REFCLKO 输出 50MHz"的模块匹配。
- PHY 地址:`ESP_ETH_PHY_ADDR_AUTO` 自动探测,别硬编码。
- nRST 内部上拉:`reset_gpio_num = -1`。

### 性能预期

ESP32 软件 NAT **10~20 Mbps**(本次实测 17 Mbps),足够几台设备浏览/视频,跑不满百兆。需要更高吞吐需换带硬件加速的方案(如 ESP32-S3 + 更优链路,或外挂 NAT 芯片)。

---

## 五、一句话总结

**ESP32 做 NAT 网关的难点不在代码量(核心就 3 条配置 + 2 个 API 调用),而在三个"反直觉"点:①NAPT 开在 LAN 网卡;②默认路由锁定 WAN;③DNS 两步下发。** 把这三点记牢,同类需求半天内能打通;忘了,可能卡一天。
