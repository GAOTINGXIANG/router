# W5500 驱动集成与本地组件迁移 —— 开发日志

> 目标:为 ESP32-WROOM-32 引入 W5500 以太网驱动(与 LAN8720 并存),并把以太网相关依赖组件改为本地管理
> 环境:ESP-IDF v6.0.2
> 日期:2026-10-14
> 状态:✅ 编译通过

---

## 一、背景与目标

项目原本用 LAN8720(RMII 内置 EMAC)做以太网,现要新增 W5500(SPI 以太网控制器)作为可选网卡,并顺势把 `lan87xx`、`w5500`、`wiznet_common` 三个组件从组件管理器(`managed_components`)迁到项目根目录 `components/` 本地管理,方便版本控制与离线编译。

最终目录结构:

```
router/
├─ components/
│  ├─ lan87xx/        ← LAN8720 PHY 驱动
│  ├─ w5500/          ← W5500 驱动(v2.0.0)
│  └─ wiznet_common/  ← W5500/W6100 公共代码(w5500 的强依赖)
├─ main/
└─ ...
```

---

## 二、问题记录

### 问题 1:manifest 方式添加 w5500 失败

**现象**:在 `main/idf_component.yml` 里写 `espressif/w5500: '^1.0.0'` 后无法正确解析/构建。

**根因**:`espressif/w5500` 的 1.x 是面向 IDF 5.x 的旧接口;面向 IDF 6.0 的是 **2.0.0**(esp-eth-drivers 仓库 master 分支),且该版本把公共代码拆成了独立的 `espressif/wiznet_common` 组件。版本写错 + 组件不自包含,导致失败。

**解决**:放弃 manifest 自动拉取,改为手动拉取组件到本地 `components/`,由构建系统直接识别。

---

### 问题 2:本地组件放置不规范

**现象/隐患**:
- LAN8720 组件目录名是 `espressif__lan87xx`(这是 `managed_components` 的命名习惯,不适合本地组件)。
- `w5500` 组件缺它的强依赖 `wiznet_common`(源码 `#include "wiznet_mac_common.h"` 并调用 `emac_wiznet_new()` 等)。

**根因**:本地组件的组件名取**目录名**(manifest 里没有 `name:` 字段时);`espressif__` 前缀会被当成组件名的一部分。`w5500` 的 `idf_component.yml` 声明了 `espressif/wiznet_common` + `override_path: ../wiznet_common`,要求 `wiznet_common` 作为兄弟目录存在。

**解决**:
1. 目录改名 `espressif__lan87xx` → `lan87xx`,并删除 `.component_hash`、`CHECKSUMS.json` 两个管理器残留文件。
2. 补齐 `components/wiznet_common`(从 esp-eth-drivers 仓库同一次提交拉取)。
3. `w5500` 里的 `override_path: ../wiznet_common` 恰好指向 `components/wiznet_common`,依赖自动满足,无需改 manifest。

---

### 问题 3:编译失败 —— `nvs_flash.h` / `esp_event.h`: No such file or directory(核心问题)

**现象**(真实编译器输出):

```
main/main.c:2:10: fatal error: nvs_flash.h: No such file or directory
CODE/src/ethernet.c:5:10: fatal error: esp_event.h: No such file or directory
CODE/src/wifi.c:4:10: fatal error: esp_event.h: No such file or directory
```

**根因**:对比旧工程(能编译成功)与当前的 `compile_commands.json`,发现 `main` 组件的编译命令里少了 `nvs_flash`、`esp_event`、`esp_netif`、`esp_eth`、`esp_wifi` 的 `-I` 路径。

原因链条:

1. 旧工程 `main/idf_component.yml` 里声明了 `idf` 依赖,它会**隐式**把一组公共 IDF 组件(esp_event、esp_netif、esp_wifi、esp_eth、nvs_flash、esp_timer 等)挂到 `main` 上。
2. 迁移本地组件时删掉了 `main/idf_component.yml`,这些隐式依赖随之消失。
3. `main/CMakeLists.txt` 里只补了 `REQUIRES lan87xx`,没补 `main` 直接 include 的 IDF 组件。

**解决**:在 `main/CMakeLists.txt` 显式声明 `main` 用到的全部组件:

```cmake
REQUIRES
lan87xx
nvs_flash
esp_event
esp_netif
esp_eth
esp_wifi
```

这 6 个正好对应代码里 `esp_eth_phy_lan87xx.h` / `nvs_flash.h` / `esp_event.h` / `esp_netif.h` / `esp_eth.h` / `esp_wifi.h` 所属的组件;其余(如 `esp_timer`)由这些组件的传递依赖自动带入。

---

### 问题 4:IDE 红色波浪线(干扰项,非编译错误)

**现象**:VSCode 里 `esp_event.h`、`esp_netif.h`、`nvs_flash.h` 等显示 "无法打开源文件 / No such file or directory"。

**根因**:IDE 的 IntelliSense/clangd 配置里 `--compile-commands-dir` 与 `compileCommands` 指向**旧项目路径** `...\ESP32_WROOM_32\ESP32_WROOM_32\build`(项目已改名为 `router`),读不到当前的 `compile_commands.json`。

**解决**:
- `.vscode/settings.json`:clangd 的 `--compile-commands-dir` 改为当前 `...\router\build`。
- `.vscode/c_cpp_properties.json`:`compileCommands` 改为 `${workspaceFolder}/build/compile_commands.json`。
- 重载窗口 / 重启语言服务器后红字消失。

> 教训:IDE 红字 ≠ 真实编译错误,一切以 `idf.py build` 的编译器输出为准。

---

## 三、经验总结

1. **`main/idf_component.yml` 里的 `idf` 依赖不是摆设** —— 它会隐式引入一组公共 IDF 组件。删除该文件改用本地组件后,必须显式 `REQUIRES` 补齐 `main` 直接 include 的组件,否则报 `No such file or directory`。
2. **区分 IDE 报错与真实编译错误** —— 排查编译问题时,直接看编译命令里的 `-I` 列表(或对比新旧 `compile_commands.json`),别被 IntelliSense 红字带偏,也别忘了检查目标组件**自身**的编译条目。
3. **本地组件目录名 = 组件名** —— 从 `managed_components` 迁移时去掉 `espressif__` 前缀,并清理 `.component_hash` / `CHECKSUMS.json` 残留。
4. **依赖组件要一起搬** —— `w5500` 强依赖 `wiznet_common`,二者版本还要对齐(同一次提交),缺一不可;`override_path` 的相对路径依赖它们互为兄弟目录。
